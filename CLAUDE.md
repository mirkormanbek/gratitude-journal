# Growth OS — repository instructions

## Mission
This repository is a personal, mobile-first “Growth OS” for one user. It started as a gratitude/growth journal and has evolved into an extensible personal operating system. New features must fit the platform architecture instead of adding isolated pages or new bottom-nav items.

## Product architecture (stable)
The primary navigation is fixed at **five items only**:
1. Today (`Сегодня`)
2. Plan (`План`)
3. Journal (`Дневник`)
4. Progress (`Прогресс`)
5. Services (`Сервисы`)

**Never add a sixth primary bottom-nav item.** New modules live under Services and optionally surface context into Today, Plan and Progress.

Read these before significant work:
- `docs/PRODUCT_CONTEXT.md`
- `docs/ARCHITECTURE.md`
- `docs/UX_PRINCIPLES.md`
- `docs/CURRENT_STATE.md`
- `docs/ROADMAP.md`
- `docs/SECURITY_AND_INTEGRATIONS.md`

## Current stack
- PHP + MariaDB
- Hosted on PS.KZ / Plesk
- Production site: `journal.luckysport.kz`
- Session auth + CSRF
- OpenAI Responses API is called only from the server
- Quran Foundation API is called only from the server
- Mobile-first dark UI; desktop sidebar is secondary

## Critical compatibility rule
Production runs **PHP 7.4.33** (verified in Plesk 2026-11-21). No PHP 8 syntax or functions (`str_contains`, `match`, `?->`, named args, union types). CI enforces this.

## Security rules
- Never put API keys or client secrets in browser JavaScript, HTML, git, screenshots, logs or docs.
- Keep OpenAI and Quran Foundation credentials server-side (`config.php`/environment).
- Never commit the production `config.php`.
- Preserve authenticated session checks and CSRF checks on writes.
- Do not silently broaden what diary data is sent to OpenAI. User-triggered analysis sends only the explicitly selected scope.

## Product behavior rules
- Today is a dashboard, not a dumping ground. It should fit roughly within 1–1.5 mobile screens before scrolling into secondary content.
- Plan combines future-facing information: calendar, tasks, projects and scheduled workouts.
- Journal is reflection: daily journal + CEO Review.
- Progress aggregates outcomes and consistency across modules.
- Services is the extensibility surface for all modules.
- A service should expose events/data to Today/Plan/Progress rather than creating parallel calendars or duplicate navigation.

## Tasks and projects
- A **task** must be a concrete action that can be checked off.
- A **project** is a multi-step outcome that cannot be closed with one checkbox.
- Example hierarchy: outcome → project → next actions.
- Daily journal field “Tasks for tomorrow” creates tasks for the day after the journal entry date.
- The journal date means “the day being reviewed”, especially when the user fills it after midnight.
- Editing a journal entry must not create duplicate tasks.
- Manual rescheduling of a task should not be overwritten by journal re-sync.

## Workouts
- Current concept: 3 workouts/week, default recurring schedule Mon=Day 1, Wed=Day 2, Fri=Day 3.
- Rest days are unmarked.
- A single missed workout can be moved to another date without shifting the permanent schedule.
- Permanent weekly schedule is editable.
- Workout calendar is the source of truth for dates.
- Workout session records planned vs actual performance at set level (weight/reps).
- Sessions, including test sessions, must be deletable with their recorded sets.

## Quran
- Daily reading should be a coherent **5–10 minute reading block**, not necessarily one ayah.
- Short surahs such as Al-Fatiha should be shown completely (1:1–1:7).
- Arabic text is never generated by AI.
- Translation should be concise; commentary must be separated from translation.
- Tafsir must identify its actual source. Never label AI text or another tafsir as official QMDB / Muftiyat Kazakhstan commentary.
- Prefer a source aligned with mainstream Sunni/Hanafi tradition when available; otherwise show the actual classical source transparently.
- AI may summarize a retrieved tafsir, clearly labeled as a summary based on that source.

## Person of the day
- The goal is an interesting 3–5 minute biography of a real person who contributed something meaningful to the world.
- It does not need to force a business lesson or “new insight”.
- Include context, contribution, impact and an interesting episode; avoid fabricated quotes/details.

## UX / UI
- Mobile-first.
- Bottom navbar is fixed to screen bottom, accounts for iPhone safe area, and content must have sufficient bottom padding so nothing hides beneath it.
- Avoid long pages made from stacked full-size forms.
- Prefer compact summaries + modal/sheet detail views.
- Hide secondary actions behind contextual menus where appropriate.
- Avoid duplicate entry points and duplicate sources of truth.
- Use the existing dark/blue visual language unless explicitly redesigning the system.

## Coding workflow
1. Inspect the current repository and DB schema before modifying anything.
2. This repository mirrors production (imported from the live server 2026-11-21) and is the source of truth.
3. For schema changes, create idempotent migrations/installers and backups.
4. Preserve existing data.
5. Test PHP syntax and JavaScript syntax.
6. For UI work, test narrow mobile widths first (~390px), then desktop.
7. Report exactly which files changed and which files must not be replaced.

## Delivery workflow (automated)
- Work on a branch, open a Pull Request; never push directly to `main`.
- Merge to `main` → checks → `production` branch → Plesk Git deploys to the site (see `docs/DEPLOY.md`). Never push to `production` by hand.
- The repository is PUBLIC: never commit secrets, personal diary data or DB dumps.
- Every schema change is a new file in `migrations/` (never edit an applied one).
- CI rejects: PHP syntax errors on 7.4, PHP 8-only functions, tracked `config.php`, API-key-like strings.
- Describe in the PR: what changed, how it was checked (390px mobile first), and any migration.
